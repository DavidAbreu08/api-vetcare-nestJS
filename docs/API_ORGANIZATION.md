# API organization and resource usage

Resource code is organized into users, employees, roles, job-titles, system-settings, animal, species, breeds, reservation, reservation-history, blocked-times, employee-schedules and clinical-visits (plus the stateless `availability` read service): one folder per table, with the resource-service layout (entities/, dto/, enums/, *.messages.ts, business service, service, controller and module when there are endpoints).

- `src/app/reservation/`: `vc_reservations` only (entity, DTOs, policy, serializer, controllers, services, module, `employee-schedule-lock.ts`); `GET /api/vetcare/clinic/hours` stays here because it exposes the reservation policy.
- `src/app/reservation-history/`: `vc_reservation_history` (entity, action enum, `ReservationHistoryService`, module without controller). `GET /api/vetcare/reservations/:id/history` remains in the reservations controller and uses the exported service.
- `src/app/animal-owners/`: `vc_animal_owners` (entity, end-reason enum, DTOs, messages, `AnimalOwnersBusinessService`, `AnimalOwnersController`, `AnimalOwnersModule`) plus the read side `AnimalAccessService`/`AnimalAccessModule` (no controller, no application imports), shared by animals, measurements, clinical visits, reservations and accounts without circular imports. See "Animal tutors".
- `src/app/blocked-times/`: `vc_blocked_times` (entity, DTOs, messages, services, controller, module; `/api/vetcare/blocked-times` routes unchanged). Blocks are UTC intervals (`start_at`/`end_at`, possibly spanning days and overlapping); `employee_id` NULL is a clinic-wide closure. `blocked-time.queries.ts` (`overlappingBlocks`) is the read shared by reservations, availability and the employee availability list. The reservation module reads the entity for the block check. See "Employee schedules, blocked times and availability".
- `src/app/employee-schedules/`: `vc_employee_schedules` (entity, DTO, messages, policy, `EmployeeSchedulesBusinessService`, module without controller; `GET/PUT /api/vetcare/employees/:id/schedules` live in `EmployeesController`).
- `src/app/availability/`: `GET /api/vetcare/availability` only (service, policy, DTO, controller, module); stateless, with no table of its own.

Each resource has a controller, an application service, a BusinessService, request DTOs and a dedicated messages file. Controllers handle routing and authentication/role guards. Application services expose resource operations and delegate each call. BusinessServices own access checks, validation, repository work and orchestration. This avoids generic base-service inheritance and keeps resource-specific rules visible.

Animal relation names live in AnimalRelation; reservation relation names live in ReservationRelation. These enums refer to TypeScript relation attributes, not SQL names. SQL mappings continue to use the already-migrated snake_case schema. No database migration is required by this reorganization.

## Persistence errors

PersistenceService.execute wraps repository work. It recognizes SQL Server error numbers centrally: duplicate unique values become HTTP 409, reference conflicts become 409, invalid persisted values become 400, and unclassified QueryFailedError failures become a safe HTTP 500 without SQL or driver details. GlobalExceptionFilter applies the same translator to queries not wrapped explicitly and formats all HTTP errors using the shared response contract. Existing HTTP business exceptions retain their original status. Resource services contain no SQL Server error-number handling; when a resource needs its own message for one rule it uses the helpers exported next to the translator (`isUniqueViolationOf(error, name)`, `isReferenceViolation(error)` — the latter gives DELETE /api/vetcare/services/:id its readable 409 when a foreign key rejects the deletion).

Messages emitted by business rules are stored in the corresponding resource messages file. Enum names represent business concepts rather than copies of entire sentences.

## Resource CRUD

All base collections accept skip (default 0) and take (default 50, maximum 100). Collection DTOs define additional filters; unknown parameters are rejected by the existing global ValidationPipe. Specialized collection routes remain available for their distinct queries and may retain their unpaginated behavior.

| Resource | Collection routes | Single-record routes |
| --- | --- | --- |
| Users | GET/POST /api/vetcare/users | GET/PATCH/DELETE /api/vetcare/users/:id |
| Animals | GET/POST /api/vetcare/animal | GET/PATCH/DELETE /api/vetcare/animal/:id |
| Species | GET/POST /api/vetcare/species | GET/PATCH/DELETE /api/vetcare/species/:id |
| Breeds | GET/POST /api/vetcare/breeds | GET/PATCH/DELETE /api/vetcare/breeds/:id |
| Reservations | GET/POST /api/vetcare/reservations | GET /api/vetcare/reservations/:id (operations: see Reservations and clinical visits) |
| Blocked times | GET/POST /api/vetcare/blocked-times | GET/PATCH/DELETE /api/vetcare/blocked-times/:id |

PATCH applies the provided update fields; omitted values are retained. Animals, users, employees, roles, job titles, species, breeds, measurement types, system settings and blocked times expose one PATCH update handler each, without PUT aliases. Whole-list role replacement and explicit action routes retain their existing HTTP verbs. Animal creation uses POST /api/vetcare/animal and administrator-created clients use POST /api/vetcare/users/clients; deprecated route aliases are not registered. See API_ROUTES.md for the complete inventory.

Species and breeds are separate resources/modules/services. A breed's parent species cannot be changed through its update DTO. Deleting a referenced catalog entry returns 409; it never cascades through animal data.

New users collection endpoints and blocked-time CRUD require administrator access. User detail/update remains owner-or-administrator. Animal reads are open to staff and to every active tutor; updates to staff and the primary tutor (see "Animal tutors"); employees and administrators retain the existing broader access. Animal deletion remains administrative and returns 409 while the animal has open reservations or a visit in progress (see "Integrity and lifecycle"). Catalog reads require authentication; catalog writes require administrator access. Reservation access is described in Reservations and clinical visits.

DELETE users and animals performs soft deletion (both refused with 409 while open reservations exist, see "Integrity and lifecycle"). Reservations and clinical visits have no DELETE route; reservations are cancelled through POST /api/vetcare/reservations/:id/cancel. DELETE blocked times removes that block. No delete endpoint removes a related owner/animal/catalog implicitly.

## DTO documentation and animal compatibility

Every Create*Dto contains English class documentation and field descriptions exposed through Swagger decorators. DTOs validate request data; business validation verifies referenced owners, catalog membership, access and status changes.

AnimalEntity documents identity, taxonomy, physical attributes and audit timestamps; measurements live in their own entity. AnimalService is the application facade; AnimalBusinessService uses explicit helpers such as requireClientOwner, mapWritableAttributes and resolveAnimalTaxonomy.

Animal request fields include ownerId, speciesId, optional breedId, name, color, sex, optional birthDate, description, notes, imageUrl, microchipNumber and isNeutered. birthDate is YYYY-MM-DD and cannot be in the future; null represents unknown. Verification state is set by server rules; species/breed changes and approval are described in "Integrity and lifecycle".

Catalog lookup aliases type and breed, plus gender and image aliases remain accepted. Labels must identify catalog entries already present; client requests do not silently create taxonomy. Age is calculated only from a known birthDate; otherwise the response is null. Response breed remains a string, while breedDetails exposes the relation. Soft-deleted animals are hidden from normal animal collections but can be recovered when reading reservation history.

Authentication, email delivery, reset-token expiry and time utilities are supporting services or actions. They do not receive artificial CRUD endpoints or BusinessServices solely to imitate resource controllers.

## Verification

Build and focused business/persistence/metadata tests run without connecting to SQL Server. They do not execute migrations. Existing unrelated deletions in the workspace are left untouched.

## Measurement types and observations

`/api/vetcare/measurement-types` supports paginated GET, GET /:id, POST, PATCH /:id and DELETE /:id. Reads require authentication; mutations require ADMIN. Types have code, name, unit, isActive (default true), description (240) and notes (500). Codes are trimmed and normalized to uppercase, with letters, digits and underscores (first character a letter); custom codes are supported independently of the built-in enum. Code uniqueness is enforced by SQL Server; duplicates return 409. Code and unit are immutable after creation: create a new type to represent a different unit or meaning. Name, activation and metadata remain editable. Referenced types cannot be deleted (409); deactivate them instead.

The seeded measurement categories are WEIGHT (weight, kg), HEIGHT (height, cm), TEMPERATURE (temperature, degrees Celsius), HEART_RATE (heart rate, bpm) and RESPIRATORY_RATE (respiratory rate, rpm). These are English descriptions; historical persisted display names are not renamed by this change.

`/api/vetcare/animal-measurements` supports GET (optional animalId, measurementTypeId, clinicalVisitId, skip, take), GET /:id, POST, PATCH /:id and DELETE /:id (JSON body `{ "reason": "..." }` required). Every operation requires JWT authentication. Reads (`@Roles` ADMIN, EMPLOYEE, CLIENT): clients see only their animals; staff and administrators use the existing animal access policy. POST and PATCH require ADMIN or an active EMPLOYEE (`@Roles` plus `requireStaff` in the business service); clients get 403. DELETE requires ADMIN (employees and clients get 403). Observations of soft-deleted animals remain stored but unavailable through this API.

DELETE is an audited soft-delete: the body `{ "reason": "<non-blank, max 500>" }` is mandatory (400 otherwise); the row keeps `deletedAt` (UTC), `deletedBy` and `deleteReason` and disappears from GET, lists and latest values (404 afterwards). Measurements of a clinical visit are never deleted (409). PATCH and DELETE re-read the row with `pessimistic_write` (UPDLOCK) inside a transaction, so concurrent edits do not lose updates.

Every response carries `clinicalVisitStatus` (IN_PROGRESS, COMPLETED, VOIDED, or null without a visit) next to `clinicalVisitId`; the visit itself is never serialized. Measurements of VOIDED visits stay listed (with that indicator) but never count as latest values.

POST accepts animalId, measurementTypeId, numeric value, optional name, measuredAt, description and notes. One row represents one type and value. Values must be finite with at most six decimal places and magnitude at most 999999999.999999; the API deliberately uses a conservative JavaScript numeric range within decimal(18,6). Stored values are returned as decimal strings to preserve precision. Negative temperatures and custom values are supported; WEIGHT, HEIGHT, HEART_RATE and RESPIRATORY_RATE must be nonnegative. The API rejects extra precision instead of rounding. The database preserves the full former weight precision, including historical values beyond the new-write API range.

Omitted measuredAt defaults to now. Explicit null, future times and timestamps without timezone are rejected. measuredAt is stored as a UTC instant. The authenticated caller supplies recordedBy (mandatory, NOT NULL); HTTP input cannot supply the author. PATCH accepts only value, measuredAt, name, description and notes: animalId, measurementTypeId, clinicalVisitId and recordedBy are rejected with 400 (`forbidNonWhitelisted`). PATCH never rewrites recordedBy; it records the editor in `updatedBy`. Omitted fields retain their values, including unknown legacy time. Creating an observation requires an active type; the type is immutable, so value corrections of observations of inactive types remain possible (validated against that type's sign rules). Explicit null value is rejected.

Animal create/update no longer accepts weight, height or legacy age. Supply an actual birthDate for age calculation. Species type and breed aliases still resolve catalog entries. Animal responses expose weight and height independently for compatibility, plus latestMeasurements containing the latest row for every type, including inactive types. Known timestamps precede unknown-time imports; ties use measuredAt, createdAt and id descending. Future stored rows (compared with `SYSUTCDATETIME()`), soft-deleted rows and measurements of VOIDED clinical visits are excluded. Collections use ranked SQL batches of at most 1000 animals, avoiding per-animal reads and SQL Server parameter limits.

For example, POST `{ "animalId": "<uuid>", "measurementTypeId": "<WEIGHT uuid>", "value": 12.125 }`, then a separate HEIGHT row with value 35.5 yields compatibility weight 12.125 and height 35.5. Multiple observations and custom signs require no schema changes. Both resources retain separate application facade, business rules, messages and centralized persistence error handling.

## Roles through system settings

Roles are data. Code never references role ids or role codes; it references only `vc_system_settings` keys (`SystemSettingCode`). `SystemRole.ADMIN`, `SystemRole.EMPLOYEE` and `SystemRole.CLIENT` map to `ADMIN_ROLE_ID`, `EMPLOYEE_ROLE_ID` and `CLIENT_ROLE_ID`. `@Roles(...)` receives these keys; `RolesGuard` resolves them through the global `SystemSettingsService` and allows the request when the caller holds ANY resolved role id. A missing or malformed role setting fails closed (500). Settings are cached in memory for 60 seconds per application instance; the instance that serves an update invalidates its own cache after the update transaction ends, while other instances (or direct SQL edits) see the change only after their cache expires, i.e. up to 60 seconds later.

JWT validation loads the user's active roles (`vc_user_roles` joined to active `vc_roles`) and the employee profile (id and termination date). `request.user`/`Actor` contains `id`, `email`, `name`, `roleIds` (lowercase), `isAdmin`, `isEmployee`, `isClient` and `employeeId` (or null). `isEmployee` requires the role of `EMPLOYEE_ROLE_ID` AND an active employee profile (termination NULL or after today); when the role is held without an active profile, the EMPLOYEE role id is also removed from `roleIds`, so `@Roles(EMPLOYEE)` denies access as soon as a termination date passes, even without any save. The JWT payload is unchanged (`sub`, `email`, `name`). Staff means administrator or employee role. Ids are compared case-insensitively because SQL Server returns uniqueidentifier in uppercase.

`GET /api/vetcare/auth/me` returns account data without the password hash, `roles` [{id, code, name}] and `employee` (or null) with `jobTitles` [{id, code, name}]. `role`, `function` and `workLoad` no longer exist in requests or responses.

## Accounts, employees and catalogs

| Resource | Routes | Access |
| --- | --- | --- |
| Roles | GET/POST /api/vetcare/roles, GET/PATCH/DELETE /api/vetcare/roles/:id | ADMIN (callers read their own roles through GET /api/vetcare/auth/me) |
| Job titles | GET/POST /api/vetcare/job-titles, GET/PATCH/DELETE /api/vetcare/job-titles/:id | read: authenticated; write: ADMIN |
| System settings | GET /api/vetcare/system-settings, GET/PATCH /api/vetcare/system-settings/:id | ADMIN |
| Animal verification | PUT /api/vetcare/animal/confirm/:id | ADMIN or veterinarian (`@Roles` ADMIN, EMPLOYEE + check in the service; 403 otherwise) |
| Employees | GET/POST /api/vetcare/employees (GET filter `isAvailableForBookings=true` also requires termination NULL or after today), GET /api/vetcare/employees/me, GET /api/vetcare/employees/available/:date, GET/PATCH/DELETE /api/vetcare/employees/:id | ADMIN; GET /me and GET /:id also for the employee itself |
| User roles | GET /api/vetcare/users/:id/roles (owner or ADMIN), PUT /api/vetcare/users/:id/roles (ADMIN) | |

Role and job-title codes are normalized to uppercase and immutable (409). Referenced entries cannot be deleted (409): deactivate them instead. A role referenced by a `*_ROLE_ID` setting can be neither deleted nor deactivated. Setting codes are immutable and settings are neither created nor deleted through the API; `*_JOB_TITLE_ID` values (`VETERINARIAN_JOB_TITLE_ID`) must be the UUID of an existing, active job title (400; the job-title row is locked during the update) or `null`/`""` to clear it, and a job title referenced by such a setting can be neither deactivated nor deleted (409; the job-title update/delete locks the job-title row and reads `vc_system_settings` from the database in the same transaction, never the settings cache); `*_ROLE_ID` values must be the UUID of an existing, active role (400), must differ from the value of every other `*_ROLE_ID` setting (409), and `ADMIN_ROLE_ID` must reference a role held by at least one active user (409). Validation and save run in one transaction that first locks (UPDLOCK) every `*_ROLE_ID` row and the previous and new role rows, so it serializes with concurrent setting updates and with the last-administrator check.

`PUT /api/vetcare/users/:id/roles` with `{ roleIds: [] }` replaces the whole list in one transaction. New assignments require active roles; existing assignments of since-deactivated roles may be kept. Kept assignments are not rewritten. The last active administrator cannot lose the administrator role, be deactivated or be deleted (409); the administrator role row is locked to serialize concurrent changes.

`POST /api/vetcare/employees` accepts exactly one of `userId` (existing account) or `user` (new account: name, email, optional phone, birthDate, nif), plus employeeNumber, licenseNumber, hireDate, terminationDate, isAvailableForBookings, jobTitleIds, description and notes. Account, role from `EMPLOYEE_ROLE_ID` (only when the created profile is active; a profile created already terminated gets no role, and a new account is then created without roles), profile, job titles and reset token are written in one transaction; the existing employee welcome email is sent after commit when an account was created. `jobTitleIds` on update replaces the assignments. DELETE removes the profile, its job titles and the EMPLOYEE role, keeping the account and its other roles; a profile referenced by any reservation or clinical visit is never deleted (409 IN_USE; the message states how many reservations and clinical visits reference it): terminate it instead. A profile cannot be created for an inactive account, nor reactivated (EMPLOYEE granted again) while its account is inactive (409). These routes replace `POST /api/vetcare/users/employees`, `PATCH /api/vetcare/users/employee/:id`, `GET /api/vetcare/users/available/:date` and `GET /api/vetcare/auth/employees`, which were removed.

Users keep only account data. Public registration (`POST /api/vetcare/users`) and `POST /api/vetcare/users/clients` assign the role from `CLIENT_ROLE_ID` in the same transaction. Emails are trimmed and lowercased, `nif` is a nine-digit string and `birthDate` is YYYY-MM-DD (not in the future). Changing `email` or `isActive` is reserved to administrators. Duplicate email or NIF among non-deleted users returns 409; email and NIF are unique only among non-deleted accounts, so they can be reused after a soft delete. Soft-deleting a user also deletes its reset tokens, and returns 409 while the user has an active employee profile (terminate or delete the profile through `/api/vetcare/employees` first).

Animal owners must hold the client role; staff see all animals and staff-created animals are verified (creation rule unchanged; species/breed changes follow "Integrity and lifecycle"). A reservation's assigned employee is an employee profile (`vc_employees.id`) that is available for bookings, belongs to an active account and has no termination date or one after today and after the reservation date, regardless of roles. Reservations are never self-assigned nor auto-confirmed. Password hashes are never selected or serialized.

Related accounts are projected per caller. In reservation responses, non-administrators see `employee` as `{ id, name, profilePictureUrl }` and `client` as `{ id, name, email, phone }`, and the nested `animal` has no `owner` (it is the client); administrators see full accounts (`id`, `name`, `email`, `phone`, `birthDate`, `nif`, `profilePictureUrl`, `isActive`, `description`, `notes`, timestamps) for client, employee and animal owner. Animal responses expose `owner` as `{ id, name, email, phone }` to non-administrators and as the full account to administrators. Measurement responses carry only `recordedBy` and `updatedBy` (ids), never the account; `updatedBy` (last editor) is visible only to ADMIN and EMPLOYEE and omitted for clients (`projectMeasurement`), in GET/list/POST/PATCH of `/api/vetcare/animal-measurements` and in `latestMeasurements` of animal responses.

## Integrity rules for roles and employees

- An employee profile is active while `termination_date` is NULL or after today (clinic date). An active profile always carries the role of `EMPLOYEE_ROLE_ID`: creating an active profile, or reactivating it (clearing or postponing the termination), grants the role in the same transaction; an update that leaves the profile terminated removes the role in the same transaction (logged after commit with actor, user and timestamp). A termination date that passes without a save is covered by JWT validation (see `isEmployee`). `PATCH /api/vetcare/employees/:id` and the profile check of `PUT /api/vetcare/users/:id/roles` lock the `vc_employees` row (UPDLOCK), so they serialize without relying on blocking reads (READ_COMMITTED_SNAPSHOT). `PUT /api/vetcare/users/:id/roles` returns 409 when it would remove EMPLOYEE from a user with an active profile, and also 409 when it would grant EMPLOYEE to a user without an active profile (the role is never granted for an account alone). Updating `EMPLOYEE_ROLE_ID` returns 409 unless every active employee already holds the new role. `DELETE /api/vetcare/employees/:id` removes the profile, its job titles and the EMPLOYEE role in one transaction.
- When the termination date is today or earlier, `isAvailableForBookings` is forced to false on save; explicitly requesting true for a terminated employee returns 400. Reservation assignment still checks bookability. `users.is_active` (may authenticate) and `employees.is_available_for_bookings` (may be chosen for new bookings) stay independent otherwise. A termination date that passes later does not rewrite the stored flag; the booking check covers it.
- Role assignments record `assigned_by`: the authenticated actor for `PUT /api/vetcare/users/:id/roles`, employee creation/reactivation and `POST /api/vetcare/users/clients`; NULL for public registration and the seed. Replacing roles deletes only removed assignments and inserts only new ones, so kept rows retain their original `assigned_by` and `created_at`. Every assignment and removal of the `ADMIN_ROLE_ID` role is logged through the Nest Logger (actor, target and timestamp) after commit. Role management (roles catalog, user roles and system settings) is restricted to ADMIN; account-creation paths can only assign EMPLOYEE or CLIENT.
- An account may be client and employee at once (e.g. a veterinarian with her own pet): neither `PUT /api/vetcare/users/:id/roles` nor `POST /api/vetcare/employees` (existing user) makes the roles exclusive, and granting EMPLOYEE never removes CLIENT. Animal owners and reservation clients only need CLIENT, and `/api/vetcare/auth/me` returns every active role plus the employee profile. Access to other clients' data comes only from the professional path (administrator, or EMPLOYEE with an active profile); otherwise CLIENT limits the caller to their own data and adds nothing for staff. When staff act on their own account as clients they follow the client path: a reservation for their own animal (no `ownerId` or `ownerId` = self, CLIENT required) is not self-assigned and stays `PENDING`, and an animal they register for themselves is not auto-verified (administrators excepted). Responses are projected by `isAdmin` only, so such an account sees reduced related accounts.
- SQL Server error 547 is split by the driver message: CHECK constraint violations return 400 ("A value does not satisfy the rules required for this record"); FOREIGN KEY/REFERENCE violations keep returning 409.
- Local login rejects inactive and soft-deleted accounts, and JWT validation reloads the account on every request, so a token issued before deactivation or deletion stops working immediately.
- JWT validation also rejects a token whose `iat` (seconds) is earlier than the second of `vc_users.password_changed_at`, so a password reset or change ends every session issued before it, including the one used for `POST /api/vetcare/auth/change-password` (that endpoint returns a replacement token, see below). A login in the same second as the change keeps working; accounts without `password_changed_at` are unaffected.

## Password recovery

Responses use the global envelope (`status`, `friendlyMessage`, `success`, `result`, see `docs/HTTP_RESPONSES.md`); statuses are those of `docs/API_ROUTES.md`.

- `POST /api/vetcare/auth/forgot-password` always answers 202 with `friendlyMessage` "If this user exists, they will receive an email!" and `result: null`: unknown, inactive or soft-deleted accounts, the per-account limit and database or SMTP failures are indistinguishable. The response is returned immediately and the whole issuance (account lookup, limit, invalidation, insert, email) runs in the background, so the response time does not depend on the account either. For an active account it locks the account row (`UPDLOCK, ROWLOCK`, which also serializes concurrent requests for the per-account limit), invalidates the pending tokens (`used_at`) and stores a new one in one transaction; failures are logged as a constant (never the address or the token). At most 3 tokens are created per account per hour (`created_at`, welcome tokens included); beyond that nothing is issued or sent.
- Tokens are 32 random bytes as 64 lowercase hexadecimal characters, valid for one hour and single-use. Only their SHA-256 (`vc_reset_tokens.token_hash`) is stored; the plain token travels only in the email link (`/auth/reset-password?token=...`). Welcome emails of accounts created without a password (`POST /api/vetcare/users/clients`, `POST /api/vetcare/employees` with `user`) use the same tokens.
- `PUT /api/vetcare/auth/reset-password` validates `resetToken` with `^[0-9a-f]{64}$` (400 otherwise) and the password confirmation before touching the token (400 on mismatch). In one transaction it reads the token's account without locks, locks the account row, marks the token used (`used_at`) only if it is still pending, unexpired and of that account, sets the password and `password_changed_at` only for an active, non-deleted account, and invalidates the account's other pending tokens. Unknown, expired and used tokens, and inactive or deleted accounts, all return 400 (`errorMetadata` INVALID_VALUE, `friendlyMessage` "Invalid, expired or already used reset token") and change nothing. Success answers 200 with `friendlyMessage` "Password reset successfully!" and `result: null`.
- `POST /api/vetcare/auth/change-password` sets `password_changed_at` and invalidates pending tokens in the same transaction as the new password. After the commit it answers 200 with `friendlyMessage` "Password changed successfully!" and `result: { token }`, where `token` is a new JWT with the same payload (`sub`, `email`, `name`) and expiry (1h) as `POST /api/vetcare/auth/login` (200, `result: { token }`), signed by the same method; `result` is null if signing fails after the change was committed. Its `iat` is `max(now, password_changed_at)` in whole seconds (`password_changed_at` is stored with full precision in `datetime2(7)`), so it is accepted even in the same second as the change or if the server clock steps back; the token used for the request keeps being rejected. The frontend should replace the stored token with `result.token`, or may ignore it and force a new login.
- Lock order: every transaction that writes `vc_reset_tokens` (forgot, reset and change password, account deletion) locks the `vc_users` row first and only then touches `vc_reset_tokens`, so these flows cannot deadlock each other. This is part of the global lock order in "Lock order".
- Rate limiting (`@nestjs/throttler`, in-memory, per IP) applies only to these public routes through `ThrottlerGuard` on the route: forgot-password 5 requests and reset-password 10 requests per 15 minutes (429 beyond). The client IP is Express `req.ip`; `trust proxy` is off by default (socket address). Behind a reverse proxy set `TRUST_PROXY`: a number of hops (e.g. `1`), `true` (trusts every hop; only when the proxy always overwrites `X-Forwarded-For`) or a comma-separated list of proxy IPs/subnets or Express names (`loopback`, `10.0.0.0/8`); `false` or empty keeps it off. `ThrottlerModule.forRoot` is registered in `AppModule` without `APP_GUARD`.
- `ResetTokenService` (registered in `AuthModule`) runs hourly and deletes expired tokens and tokens used more than 24 hours ago, logging through the Nest Logger.

## Reservations and clinical visits

Instants (`startAt`, `endAt`, `confirmedAt`, `cancelledAt`, `startedAt`, `endedAt`, `voidedAt`) are ISO-8601 with an explicit offset or `Z`; values without an offset are rejected (400). They are stored in UTC and returned as UTC ISO strings. `createdAt`/`updatedAt` keep the local-time convention. Business hours (Mon-Fri 07:00-20:00, one clinic day) are evaluated in Europe/Lisbon.

| Route | Access | Rule |
| --- | --- | --- |
| GET /api/vetcare/reservations | authenticated roles | filters status, clientId, employeeId, createdBy, animalId, from, to (startAt), skip/take (`createdBy` only narrows the scope; non-admins may only filter by their own id, any other id returns an empty page); scoped: ADMIN all, active employee assigned to them, client own, and every reservation of animals the caller is an active tutor of |
| GET /api/vetcare/reservations/:id, GET /api/vetcare/reservations/:id/history | same scope (403 otherwise) | history is chronological; non-admins see `changedBy` only when it is themselves (`changedBySelf`), and in `CLIENT_CHANGED` events `oldData.clientId`/`newData.clientId` only when it is their own id (null otherwise) |
| POST /api/vetcare/reservations | ADMIN, EMPLOYEE, CLIENT | always PENDING; `createdBy` = caller (never accepted in the body: 400); `serviceId` required (404 unknown, 409 `SERVICE_INACTIVE`); `endAt` = startAt + service `durationMinutes` (optional in the body: the same value is accepted from anyone, a different one only from ADMIN, 400 `END_AT_MISMATCH` otherwise); `employeeId` (pre-assignment, CREATED + EMPLOYEE_ASSIGNED) only for ADMIN (403 otherwise) and qualified for the service (400 `EMPLOYEE_NOT_QUALIFIED`), like PATCH /employee |
| PATCH /api/vetcare/reservations/:id/employee | ADMIN | PENDING only; bookable employee qualified for the reservation's service (400 `EMPLOYEE_NOT_QUALIFIED`; not checked when `serviceId` is null); EMPLOYEE_ASSIGNED or EMPLOYEE_CHANGED; never confirms |
| POST /api/vetcare/reservations/:id/confirm | ADMIN | PENDING with employee (still qualified for the service), future, not blocked, no overlap, animal not deleted (409 `ANIMAL_UNAVAILABLE`), client active (409 `CLIENT_INACTIVE`), no clinical visit (VOIDED included; 409 `RESERVATION_HAS_VISIT`); sets confirmedAt |
| POST /api/vetcare/reservations/:id/reschedule | ADMIN | PENDING/CONFIRMED without any clinical visit (VOIDED included; 409 `RESERVATION_HAS_VISIT`); optional `endAt` (default: the reservation's own duration, end - start); assigned employee still qualified; animal not deleted and client active (409 as confirm); CONFIRMED returns to PENDING (confirmedAt cleared); RESCHEDULED with old/new |
| POST /api/vetcare/reservations/:id/cancel | ADMIN or the reservation's client | PENDING/CONFIRMED without an IN_PROGRESS/COMPLETED visit; the client only before startAt (409 `CANCEL_AFTER_START`), ADMIN at any time; sets cancelledAt |
| POST /api/vetcare/reservations/:id/no-show | ADMIN | CONFIRMED, without an IN_PROGRESS/COMPLETED visit, after startAt + `RESERVATION_NO_SHOW_TOLERANCE_MINUTES` |

| POST /api/vetcare/clinical-visits | ADMIN, EMPLOYEE | from a CONFIRMED reservation without any visit (VOIDED included; same animal), started only by the employee assigned to the reservation or ADMIN; or without reservation (animalId). Responsible = caller (reservation's employee by default), or any active employee chosen by ADMIN. At most one IN_PROGRESS visit per animal (409 IN_USE, message only; find the visit with GET /api/vetcare/clinical-visits?animalId=...&status=IN_PROGRESS); a concurrent start that violates `uq_vc_clinical_visits_reservation_id` gets the same 409 (`RESERVATION_HAS_VISIT`) |
| PATCH /api/vetcare/clinical-visits/:id | ADMIN or responsible | IN_PROGRESS only (clinicalNotes, description) |
| POST /api/vetcare/clinical-visits/:id/complete | ADMIN or responsible | IN_PROGRESS -> COMPLETED (endedAt, completedBy = caller's account); its reservation CONFIRMED -> COMPLETED + COMPLETED event |
| POST /api/vetcare/clinical-visits/:id/void | ADMIN | IN_PROGRESS -> VOIDED with mandatory reason (voidedAt never before startedAt, voidedBy) |

Authorship: `vc_reservations.created_by` (migration `1795521600000`) is the account that created the reservation, distinct from `client_id` (the responsible tutor): a client booking their own animal is both; staff or an administrator booking for a client is the author only. POST always writes the authenticated caller; no later operation (assign, confirm, reschedule, cancel, no-show, visit completion, `CLIENT_CHANGED` tutor moves) changes it. NULL means system/unknown (reservations created before the migration without a `CREATED` event). It equals `changedBy` of the `CREATED` history event (at most one per reservation, filtered unique index); the history snapshots do not repeat it. Responses carry `createdBy` and `createdBySelf` with the `changedBy` rule of history events: administrators see `createdBy`; others see it only when it is their own id (null otherwise, so the id of the employee who booked for a client is not exposed) and every caller gets `createdBySelf`; the creator account is never serialized to non-administrators. Authorship grants no access: an employee who books for a client sees the reservation afterwards only when it is assigned to them (the read rules above are unchanged).

States: PENDING -> CONFIRMED | CANCELLED; CONFIRMED -> COMPLETED | CANCELLED | NO_SHOW (409 otherwise). COMPLETED is reachable only through visit completion. Every change and its history event share one transaction; the reservation row is read with UPDLOCK. Confirmation, assignment, reschedule and creation with an employee take the clinic closures applock (`vc_blocked_times:global`, Shared) and then `sp_getapplock` on `vc_reservations:employee:<employeeId>` (Exclusive, Transaction owner, 5 s) before checking the employee's schedule, clinic closures and the employee's blocks, and overlaps: timeout/deadlock return 409, other failures 503. Overlap counts only CONFIRMED reservations of the employee, widened by `RESERVATION_BUFFER_MINUTES`. Creation and reschedule without an employee only check clinic closures (see "Employee schedules, blocked times and availability"). Notifications are sent after commit (`notificationStatus`); user values in email HTML are escaped. Cancel, no-show and visit completion only free time and therefore run without the applock (safe: they can never create an overlap). Rescheduling a PENDING reservation whose employee is no longer bookable fails (400): reassign the employee first (PATCH /employee). Any clinical visit, VOIDED included, blocks confirm and reschedule (409 `RESERVATION_HAS_VISIT`, message "The reservation already has a clinical visit (voided visits included); it cannot be confirmed or rescheduled"; before, a reservation with an IN_PROGRESS visit got the VISIT_STARTED message, "The reservation has an active clinical visit; ..."). Only IN_PROGRESS and COMPLETED visits block cancel and no-show, so a VOIDED visit does not. A reservation never gets a second visit: `uq_vc_clinical_visits_reservation_id` also covers VOIDED rows, and a concurrent start that violates it returns 409 with the message "The reservation already has a clinical visit". SQL deadlock victims (1205) and lock timeouts (1222) return 409.

Clinical access (no RBAC): ADMIN sees everything; an employee with an active profile sees visits they are responsible for and visits of animals with a reservation assigned to them in CONFIRMED, COMPLETED or NO_SHOW (a PENDING assignment grants nothing); every active tutor (primary or secondary) of the animal sees its visits without `clinicalNotes`/`voidReason`. `voidedBy` and `completedBy` are shown only to ADMIN. Employees in responses are `{ id (vc_employees.id), name, profilePictureUrl }` (ADMIN also `userId` and the account).

`/api/vetcare/animal-measurements` (writes restricted to staff, see "Measurement types and observations") accepts an optional immutable `clinicalVisitId` (also a list filter). Linking requires an IN_PROGRESS visit of the same animal and clinical access; the save runs under the visit lock. Measurements of a visit can be edited only while it is IN_PROGRESS and are never deleted (409).

`RESERVATION_NO_SHOW_TOLERANCE_MINUTES` and `RESERVATION_BUFFER_MINUTES` accept only integers 0..2147483647 through `/api/vetcare/system-settings` (400 otherwise); an invalid stored value fails closed (500). The former routes `/api/vetcare/reservation/*` (create, update-status, all, client, employee, confirm-pending, confirm-rescheduled, reject-rescheduled, :employeeId/:date, PUT/DELETE :id) were removed.

## Integrity and lifecycle

Nothing is ever cancelled or reassigned automatically: changes that would strand open reservations return 409 so the caller can cancel or reassign them first. "Open reservation" = PENDING or CONFIRMED whose `end_at` is still in the future (UTC); a stale reservation whose end has passed does not block. Known limitation (accepted): an overdue CONFIRMED reservation (end passed, never completed, cancelled or marked NO_SHOW) is therefore not counted as open and does not block these changes; administrators should close such reservations (no-show/cancel). Conflict responses are the global error envelope only (`status` 409, `errorMetadata` IN_USE or CONFLICT, `friendlyMessage`, `result: null`): they never carry id lists or count fields. When useful the number of affected records is part of the readable message (e.g. "The client has 2 open reservations (pending or confirmed, not yet finished); cancel them before deactivating or deleting the account."); clients find the records through GET /api/vetcare/reservations (filters `clientId`, `employeeId`, `animalId`, `status`, `from`) or GET /api/vetcare/clinical-visits. The internal names in the table below identify each rule in code and tests; they are not part of the HTTP body.

| Change | Rule | Internal rule name (message only in HTTP) |
| --- | --- | --- |
| PATCH /api/vetcare/employees/:id: termination date or `isAvailableForBookings=false` | refused when an open reservation assigned to the profile was attendable before the change and no longer is after it (termination on or before its clinic date, or unavailability). PENDING assignments count as well as CONFIRMED, so no reservation stays assigned to someone who cannot attend it. Edits that keep the profile bookable, and edits of an already unavailable profile, are not blocked | `EMPLOYEE_HAS_OPEN_RESERVATIONS` |
| PATCH /api/vetcare/users/:id `isActive=false`, DELETE /api/vetcare/users/:id | refused while the account is the client of open reservations, or its employee profile has open reservations assigned; the message states how many | `CLIENT_HAS_OPEN_RESERVATIONS`, `EMPLOYEE_HAS_OPEN_RESERVATIONS` |
| DELETE /api/vetcare/animal/:id | refused while the animal has open reservations or an IN_PROGRESS visit; the message states how many of each | `ANIMAL_HAS_OPEN_ACTIVITY` |
| DELETE /api/vetcare/employees/:id | refused while any reservation or visit references the profile; the message states how many reservations and visits | `EMPLOYEE_HAS_HISTORY` |
| POST /api/vetcare/employees (existing account), profile reactivation, PUT /api/vetcare/users/:id/roles adding roles | refused for an inactive account (removing roles stays allowed) | (message only) |
| POST /api/vetcare/clinical-visits | one IN_PROGRESS visit per animal; also enforced by `uq_vc_clinical_visits_animal_in_progress`, whose 2601 violation (concurrent start) maps to the same 409 (message only, no visit id) | `ANIMAL_VISIT_IN_PROGRESS` |

Reservation creation, confirmation and reschedule re-check inside the transaction, under lock, that the animal exists and is not soft-deleted (409 `ANIMAL_UNAVAILABLE`) and that the client account is active and not deleted (409 `CLIENT_INACTIVE`). Creation also re-reads, after those locks, that the client is still an active tutor of the animal (409 `ANIMAL_OWNER_MISMATCH`; the earlier pre-check returns 400).

Species and breed: the animal's owner and any staff with write access may change them (no 403). A change by an administrator, or by a veterinarian acting on another client's animal, takes effect verified (`isVerified=true`); a change by anyone else (the client, a non-veterinarian employee, or a veterinarian on their own animal, which follows the client path) leaves the animal `isVerified=false` until approved through `PUT /api/vetcare/animal/confirm/:id`, which accepts ADMIN and veterinarians (not for their own animal) and returns 403 otherwise. Sending the current species/breed is not a change. A veterinarian is an active employee (`isEmployee`) whose profile holds the job title referenced by the setting `VETERINARIAN_JOB_TITLE_ID` (`EmployeeQualificationService` in `src/app/employees/employee-qualification.service.ts`, exported by the standalone `EmployeeQualificationModule` for reuse without circular imports). Without a valid setting nobody is a veterinarian and only administrators approve; the referenced job title must also be active (`is_active = 1`, checked with the assignment, fail closed). `VETERINARIAN_JOB_TITLE_ID` can be cleared (`null` or `""`, stored as NULL) through PATCH /api/vetcare/system-settings/:id. Creation follows the same rule: an animal is created verified only by an administrator or a veterinarian registering another client's animal (a receptionist's or a client's registration stays `isVerified=false`). Update and confirm lock the animal row (UPDLOCK) in a transaction, so an approval and a concurrent species/breed change serialize. `PUT /api/vetcare/animal/confirm/:id` accepts an optional body `{ expectedSpeciesId?, expectedBreedId? }` with the values the approver reviewed (`expectedBreedId: null` = no breed); when they no longer match it returns 409 (CONFLICT, message only: read the animal again to get the current values). Without a body the contract is unchanged.

Clinical visits record `completed_by` (the account completing it); `voided_at` is never before `started_at` (`ck_vc_clinical_visits_voided_dates`).

## Animal tutors

An animal has any number of active tutors (`vc_animal_owners`, migration `1795435200000`) and at most one active primary tutor (filtered unique index); while it has active tutors one of them is primary (application rule, enforced in a transaction holding the animal lock). Rows are immutable periods (`assigned_at`, `ended_at`, `assigned_by`, `ended_by`, `end_reason` TRANSFERRED/REMOVED/ROLE_CHANGED/ACCOUNT_DELETED/MIGRATED): a tutorship is ended, never deleted; promoting/demoting closes the row and opens a new one. `vc_animals.owner_id` is kept as a synchronized copy of the active primary tutor (same transaction); every access decision uses `vc_animal_owners` through `AnimalAccessService` (`isActiveTutor`, `isPrimaryTutor`, `activeTutorIds`, `canReadAnimal`, `canManageAnimal` and the `activeTutorExists(...)` SQL fragment, an `EXISTS` on `uq_vc_animal_owners_active`). A tutor must be an active account holding CLIENT (400 otherwise). The 409 names below (`ALREADY_TUTOR`, `ANIMAL_HAS_NO_PRIMARY`, `PRIMARY_TUTOR_NOT_REMOVABLE`, `ALREADY_PRIMARY`, `TUTOR_HAS_OPEN_RESERVATIONS`, ...) are internal rule names; the HTTP body only carries `errorMetadata` and a readable `friendlyMessage`.

| Route | Access | Rule |
| --- | --- | --- |
| GET /api/vetcare/animal/:id/owners | staff, active tutors | active tutors `[{ user, isPrimary, assignedAt }]`, primary first; `?includeHistory=true` adds closed periods (`endedAt`, `endReason`; ADMIN also `assignedBy`/`endedBy`) for staff and the primary tutor only (403 otherwise) |
| POST /api/vetcare/animal/:id/owners `{ userId }` | staff, primary tutor | adds a secondary tutor; 409 `ALREADY_TUTOR` (also when `uq_vc_animal_owners_active` rejects a concurrent insert, 2601), 409 `ANIMAL_HAS_NO_PRIMARY` when the animal has none |
| DELETE /api/vetcare/animal/:id/owners/:userId | staff, primary tutor, the secondary tutor themselves | ends a secondary tutorship (REMOVED); the primary tutor cannot be removed (409 `PRIMARY_TUTOR_NOT_REMOVABLE`: transfer first). `transferFutureReservations` in the body or query string (`true`/`false`) |
| POST /api/vetcare/animal/:id/transfer `{ newPrimaryUserId, keepPreviousAsSecondary?, transferFutureReservations?, reason? }` | ADMIN | closes the current primary period (TRANSFERRED), closes the new tutor's secondary period if any, opens the new primary period, optionally reopens the previous primary as secondary, updates `owner_id`; no consent of the new tutor; 409 `ALREADY_PRIMARY`; with `keepPreviousAsSecondary: true` 409 `PREVIOUS_TUTOR_UNAVAILABLE` when the previous primary's account no longer exists and 409 `PREVIOUS_TUTOR_NOT_CLIENT` when it is inactive or no longer holds CLIENT (nothing is changed; resend without the flag). - Reads: the animal (`GET /api/vetcare/animal`, `/:id`, `/owner/:ownerId`), its measurements and its clinical visits (without clinical notes) are visible to staff and every active tutor; `ownerId` filters (GET /api/vetcare/animal, /owner/:ownerId) mean "active tutor (primary or secondary)". Former tutors lose access to the animal, measurements, visits and reservations; the clinical record follows the animal (a new tutor sees earlier visits). Animal responses keep `owner` (the primary tutor) and add `tutors`.
- Edition: staff and the primary tutor (secondary tutors 403). Species/breed approval rules are unchanged; staff who are an active tutor of the animal (primary or secondary) follow the client path (no immediate approval). `PATCH /api/vetcare/animal/:id` with `ownerId`: the current primary is a no-op (compatibility); another account is a transfer for ADMIN (same transaction, with history; never moves reservations: 409 `TUTOR_HAS_OPEN_RESERVATIONS`, use POST /transfer with the flag) and 403 for everyone else.
- Reservations: any active tutor may book; the reservation's `client_id` is the responsible tutor, who must be an active tutor of the animal (pre-check 400, re-checked under the animal and client locks: 409 `ANIMAL_OWNER_MISMATCH`). Every active tutor sees the animal's reservations and their history; only the reservation's client or ADMIN cancels. The client of a reservation keeps seeing that reservation after leaving the animal (they stay responsible for it); they no longer see the animal's other reservations.
- Leaving with open reservations (PENDING/CONFIRMED not yet finished, as in "Integrity and lifecycle") of the animal whose client is the leaving tutor: 409 by default (IN_USE; the message states how many open reservations the tutor is the client of; no id list — use GET /api/vetcare/reservations?animalId=...&clientId=...); with `transferFutureReservations: true` their `client_id` moves to the new primary tutor (transfer) or to the current primary tutor (removal of a secondary; 409 `PRIMARY_TUTOR_INACTIVE` when that account is inactive) in the same transaction, each with a `CLIENT_CHANGED` history event (`changedBy` = caller, `oldData { clientId }`, `newData { clientId }`, transfer `reason`). The success `result` of DELETE is `{ movedReservationIds }` (data, not an error detail).
- Accounts: DELETE /api/vetcare/users/:id is refused while the account is the active primary tutor of non-deleted animals (409 IN_USE; the message states how many animals; find them with GET /api/vetcare/animal?ownerId=...); its active secondary tutorships are closed in the same transaction (ACCOUNT_DELETED). Removing the CLIENT role (PUT /api/vetcare/users/:id/roles) applies the same rule (ROLE_CHANGED) and is also refused (409 IN_USE `TUTOR_HAS_OPEN_RESERVATIONS`, count in the message) while the account is the client of open reservations of animals it is an active secondary tutor of: cancel them or end the tutorship with `transferFutureReservations: true` first (deletion already refuses any open reservation as client). Deactivation (`isActive=false`) does not change tutorships: it is reversible and an inactive account cannot sign in; while inactive it cannot be made tutor, receive moved reservations or have new reservations (existing rule `CLIENT_INACTIVE`). Primary rows of soft-deleted animals are left untouched.
- Note (tutors of soft-deleted animals): deleting an animal does not close its tutorship rows; its active primary row stays open but neither blocks account deletion/CLIENT removal nor grants access (animal reads exclude soft-deleted animals), and its secondary rows are closed with the account like any other. Known behaviour, unchanged for now.
- Concurrency guard: every close of a tutorship row (removal, transfer, account deletion, CLIENT removal) is an `UPDATE ... WHERE ended_at IS NULL`; a period closed by a concurrent flow is never rewritten. In removal/transfer, 0 rows affected returns 409 CONFLICT (`TUTORS_CHANGED`, "Tutors changed; reload and retry") and rolls back the whole transaction.

## Clinic services and qualifications

Bookable services live in `vc_services` (migration `1795608000000`; module `src/app/clinic-services`, entity `ClinicServiceEntity`, route `/api/vetcare/services`, Swagger tag "Services"): immutable uppercase `code` (catalog rule, `uq_vc_services_code`), `name`, optional `description`, `durationMinutes` (5..1440, multiple of 5; `ck_vc_services_duration`) and `isActive`. There is no price in this phase. Employee qualifications live in `vc_employee_services` (`employee_id`, `service_id`). The 409 names below (`SERVICE_INACTIVE`, `SERVICE_IN_USE`, `QUALIFICATION_HAS_OPEN_RESERVATIONS`, ...) are internal rule names; the HTTP body only carries `errorMetadata` and a readable `friendlyMessage`.

| Route | Access | Rule |
| --- | --- | --- |
| GET /api/vetcare/services | authenticated | non-administrators: active services only; ADMIN: all, optional `isActive` filter; skip/take; ordered by name |
| GET /api/vetcare/services/:id | authenticated | an inactive service is 404 for non-administrators |
| GET /api/vetcare/services/:id/employees | ADMIN, EMPLOYEE | qualified employees bookable today (available profile, active account, not terminated), projected like reservation employees; no schedule or occupation check (use GET /api/vetcare/availability) |
| POST /api/vetcare/services | ADMIN | 201; `isActive` defaults to true |
| PATCH /api/vetcare/services/:id | ADMIN | under the service row lock; `code` immutable (409); a new `durationMinutes` applies to new reservations only; deactivation blocks new reservations only and never removes qualifications |
| DELETE /api/vetcare/services/:id | ADMIN | 204 only when no reservation (any state) and no qualification references it; otherwise 409 IN_USE with the counts in the message (deactivate instead); a reference committed concurrently is caught by the foreign key and gets the same message |
| GET /api/vetcare/employees/:id/services | ADMIN, the employee itself | qualifications, including services deactivated later |
| PUT /api/vetcare/employees/:id/services `{ serviceIds }` | ADMIN | full replacement in one transaction; the services to add are read with a shared lock (by id) before the employee profile lock; unknown services: 404; new qualifications for inactive services: 409 `SERVICE_INACTIVE`; inactive services already held may be kept; qualifications changed concurrently so that an unlocked service must be added: 409 `QUALIFICATIONS_CHANGED` ("Qualifications changed; reload and retry"); removing a qualification while the employee has open reservations (PENDING/CONFIRMED, not finished) of that service: 409 IN_USE (count in the message); kept rows are not rewritten |

- Reservations: `serviceId` is required on POST /api/vetcare/reservations (no compatibility with the previous free-duration body). The service must exist (404) and be active: an inactive service is 409 `SERVICE_INACTIVE` for administrators and 404 for everyone else (inactive services are not revealed, as in GET /services/:id). The server computes `endAt = startAt + durationMinutes`; non-administrators may omit `endAt` or send exactly that value (400 `END_AT_MISMATCH` otherwise); administrators may send a different `endAt` (override), still subject to the clinic window rules. The interval is frozen in `start_at`/`end_at`: changing `durationMinutes` never alters existing reservations, and POST /reschedule without `endAt` keeps the reservation's own duration.
- `service_id` is immutable (`update: false`); changing the service of an existing reservation is not supported and no `SERVICE_CHANGED` history action exists. History snapshots written from now on include `serviceId`.
- Qualification: when the reservation has a service, the employee (pre-assignment on creation, PATCH /employee, confirm, reschedule) must hold it in `vc_employee_services` (400 `EMPLOYEE_NOT_QUALIFIED`, "The employee is not qualified for this service"), checked inside the transaction after the employee profile lock and before the applock. Reservations created before the catalog (`service_id` NULL) are not checked. An inactive service blocks only new reservations: assign, confirm and reschedule of existing ones do not read the service.
- Responses: `serviceId` and `service { id, code, name, durationMinutes }` (same for every caller; current catalog values, null for legacy reservations). `service` is always present: every reservation loader (detail, list, write responses) joins the relation, and the serializer fails instead of silently omitting it.
- Referenced ids in a body follow one rule: a missing service is 404 and an inactive service being newly referenced is 409 `SERVICE_INACTIVE` (POST /reservations, PUT /employees/:id/services).
- Pending decision: starting a clinical visit does not re-check the employee's qualification for the reservation's service (left for a future decision).
- Deactivating an employee or a service keeps the qualifications; deleting an employee profile (only possible without reservations or visits) removes its qualifications together with its job titles.

## Employee schedules, blocked times and availability

Migration `1795694400000` (`SchedulesAndBlocks`) creates `vc_employee_schedules` (FK `fk_vc_employee_schedules_employee`, no cascade, index `ix_vc_employee_schedules_employee_day`) and extends `vc_blocked_times` with `employee_id`, `start_at`, `end_at`, `created_by` and `created_at`. It backfills `start_at`/`end_at` from the legacy `start`/`end`, adds `ck_vc_blocked_times_interval`, the FKs `fk_vc_blocked_times_employee` and `fk_vc_blocked_times_created_by` (no cascade) and the indexes `ix_vc_blocked_times_start_end` and `ix_vc_blocked_times_employee_start`.

- `vc_employee_schedules` (`EmployeeScheduleEntity`) holds the weekly working periods of an employee profile in clinic local time (Europe/Lisbon). `dayOfWeek` (`day_of_week`) runs from 0 = Sunday to 6 = Saturday. `startTime` and `endTime` (`time(0)`, "HH:mm") end after they start, on the same day. `validFrom` is the first clinic date on which the period applies (inclusive, required); `validUntil` is the last one (inclusive; null = open-ended). Several rows for one weekday are several periods; periods of the same weekday with intersecting validity must not overlap (touching periods are allowed).
- Working periods of a date: when no row is valid on that date, the employee works the clinic hours (`CLINIC_POLICY`). When some row is valid, only the rows of that weekday count, so a weekday without a row is a day off. `CLINIC_POLICY` (Monday to Friday, 07:00-20:00) is always the outer envelope: periods are clipped to it and closed days have no working period. `PUT` with an empty list removes the schedule.
- Schedule validation returns 400 (`INVALID_VALUE`): end not after start, a time from 01:00 to 01:59 (the daylight-saving hour), `validUntil` before `validFrom`, overlapping periods, malformed dates, or more than 100 periods.
- `vc_blocked_times` (`BlockedTimeEntity`) stores `[startAt, endAt)` as UTC instants (`start_at`/`end_at`, `datetime2(3)`, `endAt` after `startAt`). A block may span several days and may overlap other blocks. `employeeId` NULL is a clinic-wide closure; otherwise the block is the unavailability of that employee profile. `createdBy` (`created_by`) is the authenticated caller, set by the server, never updated, and NULL for legacy rows. `reason` (255), `name` (255), `description` (240) and `notes` (500) are optional metadata; they predate this migration. The legacy single-day columns (`date`, `time_start`, `time_end`, `start`, `end`) are deprecated: NULL-able, never mapped, never read or written.

| Route | Access | Rule |
| --- | --- | --- |
| GET /api/vetcare/employees/:id/schedules | ADMIN, or the employee itself (`EMPLOYEE` role; others 403) | the profile's periods; unknown profile 404; empty list = clinic hours |
| PUT /api/vetcare/employees/:id/schedules | ADMIN | full replacement in one transaction (200); see the rules below |
| GET /api/vetcare/blocked-times | ADMIN | blocks intersecting `from`/`to`; `employeeId` filters individual blocks of that profile (closures excluded); skip/take; ordered by `startAt` |
| GET /api/vetcare/blocked-times/:id | ADMIN | unknown: 404 |
| POST /api/vetcare/blocked-times | ADMIN | 201; `createdBy` = caller; a closure when `employeeId` is omitted |
| PATCH /api/vetcare/blocked-times/:id | ADMIN | omitted fields keep their values; `employeeId: null` turns the block into a closure |
| DELETE /api/vetcare/blocked-times/:id | ADMIN | 204; frees time, so it never returns a reservation conflict |
| GET /api/vetcare/availability | any authenticated caller | `date` and `serviceId` (required), `employeeId` (optional); free slots only |
| GET /api/vetcare/employees/available/:date | ADMIN | bookable profiles with some free working time on the date; reservations are not considered |

- Creating or changing a block that intersects CONFIRMED reservations returns 409 (`IN_USE`). The message states how many; nothing is cancelled. A closure checks the reservations of every employee; an individual block checks only its employee's. PENDING reservations are not checked here (confirmation checks them again).
- Block errors: unknown `employeeId` 404; profile not active (terminated, or inactive account) 409 (`CONFLICT`); `endAt` not after `startAt`, or an instant without offset, 400. A PATCH that omits `employeeId` returns 409 (`CONFLICT`, "reload and retry") when the block's scope changed meanwhile.
- Replacing a schedule returns 409 (`IN_USE`) when a CONFIRMED reservation not yet finished fits the current schedule but would not fit the new one. PENDING reservations are not checked here. Nothing is cancelled.
- Reservations that occupy employee time (creation with an employee, assignment, confirmation, reschedule) return 409 (`CONFLICT`) when the interval is not inside one working period of the employee (rule `OUTSIDE_EMPLOYEE_SCHEDULE`), when it intersects a closure or the employee's block (`TIME_BLOCKED`), or when it overlaps another CONFIRMED reservation of the employee widened by `RESERVATION_BUFFER_MINUTES` (`EMPLOYEE_UNAVAILABLE`). Creation and reschedule without an employee only check closures, without the applock, because a PENDING reservation occupies no time.
- The rule names above are internal; the HTTP body carries only the global envelope (`status`, `friendlyMessage`, `success`, `result: null`, `errorMetadata`).
- Availability is indicative and computed with plain reads; confirmation re-checks under the applocks. For each employee qualified for the service (see "Clinic services and qualifications") and bookable on the date, it returns slots of the service duration, starting every `slotMinutes` (30) from the start of each working period. It excludes closures, the employee's blocks and their CONFIRMED reservations widened by `RESERVATION_BUFFER_MINUTES`; PENDING reservations occupy nothing; starts not after now are omitted. `startAt`/`endAt` are UTC and `localStart` is clinic time. Reservations and blocks are never exposed. A closed day lists the candidates with empty slots. Errors: unknown service 404; inactive service 409 (`SERVICE_INACTIVE`) for administrators and 404 for everyone else; unknown `employeeId` 404.

## Lock order

Every transaction acquires row locks (`UPDLOCK`, via `pessimistic_write`) in this single order and never in the reverse direction:

`vc_reservations` -> `vc_animals` -> `vc_clinical_visits` -> `vc_animal_measurements`; `vc_reservations` -> `vc_animals` -> `vc_users` -> `vc_services` (shared lock, creation only) -> `vc_employees` -> read of `vc_employee_services` -> clinic closures applock (`vc_blocked_times:global`, Shared) -> employee schedule applock (Exclusive, `sp_getapplock`) -> reads under the applocks (schedules, blocks, overlapping CONFIRMED reservations); `vc_services` (shared lock on the services to add, by id) -> `vc_employees` -> writes to `vc_employee_services` (PUT /employees/:id/services; same service -> profile order as reservation creation; reads open reservations without lock hints); `vc_services` alone (service update/deletion; deletion then counts references without lock hints); `vc_reservations` (by id) -> `vc_animals` -> `vc_users` (accounts, by id) -> writes to `vc_animal_owners`/`vc_reservations` (tutorship changes); `vc_users` -> `vc_reset_tokens`; `vc_users` -> `vc_employees` -> `vc_roles` (last-administrator check); `vc_users` -> `vc_animal_owners` (account deletion / CLIENT removal: read primary rows, close secondary rows); `vc_system_settings` -> `vc_job_titles` (setting update; job-title deactivation/deletion locks only the job title and then reads the settings without lock hints).

- Tutorship changes (add/remove a tutor, transfer, animal creation, PATCH /api/vetcare/animal/:id with another ownerId) lock the animal row before reading `vc_animal_owners` for a decision, and lock every account that gains a row before any `vc_animal_owners` write (two accounts are locked in id order). Removal of a secondary tutor locks, after the animal and before the decision read, the removed tutor's account and (with `transferFutureReservations`) the primary tutor's account, in id order. Account deletion and CLIENT removal lock the account and then read/close its rows without locking the animal, so they serialize on the account row with any flow that would make the account a tutor or remove it; no cycle forms because removal holds no `vc_animal_owners` row lock while waiting for the account, and the account flows never wait for an animal lock (their UPDATE seeks the account's own rows through `ix_vc_animal_owners_user_active`). Animal creation inserts the new animal row first (nobody can be waiting on it), then locks the owner's account, then inserts the primary row.
- Tutorship changes that move reservations (`transferFutureReservations: true`) lock the candidate reservations (open, of the animal, whose client is the leaving tutor) one by one in id order BEFORE the animal (reservation -> animal, the order of confirm/reschedule/visit start). After the animal lock (which also blocks new reservations of the animal, since creation locks it) they are read again; a reservation not locked in the first phase (created in between) makes the request fail with 409 (CONFLICT, "retry" message) instead of locking a reservation while holding the animal, which could deadlock with confirm/reschedule/visit start. Without the flag no reservation is locked: they are only read under the animal lock (409 when any is open).

- Reservation creation (animal -> client account -> service (shared) -> employee profile -> qualification read -> applock), confirmation and reschedule (reservation -> animal -> client account -> employee profile -> qualification read -> applock) and assignment (reservation -> employee profile -> qualification read -> applock). The employee profile is locked without relations and its account is read in a separate statement after the lock is granted, so it sees changes committed by whoever held the lock (also under READ_COMMITTED_SNAPSHOT).
- Services and qualifications: creation reads the service with `pessimistic_read` (`HOLDLOCK, ROWLOCK`, held until commit) so a concurrent deactivation or deletion (which takes `UPDLOCK` on the service and nothing else) either commits first and is seen, or waits; shared locks of concurrent bookings are compatible with each other. The qualification check (`vc_employee_services`, plain read) runs right after the employee profile lock and before the applock, like the account re-read; PUT /api/vetcare/employees/:id/services first reads the current qualifications without locks, derives the services to add and reads them with `pessimistic_read` in id order (validating existence and `isActive` in that read), and only then locks the profile: the order service (shared) -> profile is the one of reservation creation, and PATCH/DELETE /services/:id lock only the service, so no cycle forms (the previous order profile -> service read/FK check could deadlock with a service update waiting behind a booking). Under the profile lock the diff is recomputed; if a service that was not locked must now be added (qualifications changed meanwhile) the request fails with 409 `QUALIFICATIONS_CHANGED` instead of reading an unlocked service while holding the profile. It changes qualifications only while holding the profile lock and then reads the open reservations without lock hints, so removing a qualification and assigning/confirming a reservation for that employee serialize (check-then-act). Assign, confirm and reschedule never read the service row, so an inactive service never blocks them.
- Visit start: reservation -> animal (then the visit insert); complete/void: reservation -> visit; measurements: visit -> measurement.
- Employee termination/unavailability locks the profile; account deactivation/deletion locks the account and then the profile; animal deletion locks the animal (animal update and confirm lock only the animal). Each then *reads* the open reservations (and visits) without lock hints. Because every flow that creates, assigns or confirms a reservation (or starts a visit) locks the same row before writing, the check and the write serialize (check-then-act); because those readers never lock reservations, no cycle can form.
- Schedule and block applocks (`sp_getapplock`, transaction-owned, 5 s timeout): the clinic closures resource `vc_blocked_times:global` and the employee resource `vc_reservations:employee:<employeeId>`. A timeout, a cancellation or a deadlock victim returns 409 (retry); any other result, or no active transaction, returns 503. Per operation:
  - Global block (`employeeId` NULL): create and update take the closures applock Exclusive; an update then locks the block row (UPDLOCK); both then read the overlapping CONFIRMED reservations without lock hints.
  - Individual block: the employee profile (UPDLOCK), then the employee applock (Exclusive), then the read of that employee's overlapping CONFIRMED reservations.
  - Block PATCH: the applock(s) of the scope come first (for an individual scope, the profile lock before the employee applock), then the block row (UPDLOCK). If the scope changed meanwhile and `employeeId` was omitted: 409 "reload and retry".
  - Block DELETE: the block row (UPDLOCK) only; it takes no applock.
  - PUT schedules: the employee profile (UPDLOCK), then the employee applock (Exclusive), then plain reads of the current rows and of the open reservations, then delete and insert.
  - Occupying flows (creation with an employee, assignment, confirmation, reschedule): closures applock Shared, then the employee applock (Exclusive), then the reads listed in the chain above.
- Why there is no cycle: the closures applock is always taken before any employee applock, never the other way round. No flow waits for an applock while holding a `vc_blocked_times` row: a block PATCH takes its applocks before its row, and a DELETE takes no applock. Tutorship changes, and cancel, no-show and visit completion, never take these applocks. Plain reads of reservations under the applocks take shared locks, which are compatible with the update locks (`UPDLOCK`) held by reservation flows; a plain read can only wait for a row already modified (exclusive lock) by a transaction that never waits for these applocks (cancel, no-show, visit completion, tutorship changes, or a flow that already holds them), so no cycle forms. Under READ_COMMITTED_SNAPSHOT plain reads take no shared locks at all. Applocks are therefore not always the last locks of a chain: a block PATCH locks its row after them.
- Lock waits: `withLockTimeout` (`src/app/core/persistence/lock-timeout.ts`) runs the transactions of reservations, clinical visits (start, update, complete, void and the measurements linked to a visit), blocked times, animal tutors and the employee schedule PUT with `SET LOCK_TIMEOUT 5000`, sent as a batch on the transaction's own connection, so it applies to every query of the transaction. A lock wait longer than 5 s fails with 1222, which is returned as 409 (retry). `SET LOCK_TIMEOUT -1` is sent at the end on a best-effort basis. If the server had already ended the transaction (deadlock victim 1205 or a trigger THROW), that reset fails and is ignored, so the pooled connection keeps the 5 s limit until another critical transaction resets it; in the meantime a lock wait above 5 s on that connection, including non-critical work, returns 409 (retry). No data is affected.
- Clinical integrity triggers (`ClinicalIntegrity1795780800000`, see `SCHEMA_MIGRATION.md`) are the last line of defence behind the application checks. `tr_vc_clinical_visits_reservation_integrity` refuses changing a visit's `animal_id` or `reservation_id` (409, 51104) and creating a visit for a reservation that is not CONFIRMED (409, 51105). `tr_vc_reservations_visit_integrity` refuses a reservation becoming COMPLETED without a COMPLETED visit (409, 51106) and becoming CANCELLED, NO_SHOW or PENDING while it has an IN_PROGRESS or COMPLETED visit (409, 51107). Each THROW reaches the client as a 409 with its own message. Each trigger reads the other table `WITH (READCOMMITTEDLOCK)`, so when two transactions interleave, one waits for the other and the worst outcome is a deadlock (1205, 409 for the victim), never invalid data committed. `complete()` updates the visit to COMPLETED before the reservation because the reservation trigger needs a COMPLETED visit in the same transaction; the reverse order fails with 51106.
