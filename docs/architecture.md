# Architecture

> [não verificado] Lock order: the constants, files and helpers cited (`withLockTimeout`, `CRITICAL_LOCK_TIMEOUT_MS` 5000, `sp_getapplock` 5 s, trigger numbers) were checked against the code; the step-by-step lock sequence of every flow was not re-traced statement by statement.

## Request pipeline

Verified in `src/main.ts`, `src/app.module.ts` and `src/api-routing.ts`:

1. `src/force-utc.ts` is the first import of every entry point (`main.ts`, `database/data-source.ts`, `database/seed-admin.ts`) and sets `process.env.TZ = "UTC"`.
2. `configureApiRouting` sets the global prefix `api/vetcare`; controllers declare only their resource path.
3. `trust proxy` comes from `TRUST_PROXY` (`src/trust-proxy.ts`); it is off unless set.
4. Global `ClassSerializerInterceptor` and a global `ValidationPipe` (`transform`, `whitelist`, `forbidNonWhitelisted`, `forbidUnknownValues`).
5. CORS origin is `FRONTEND_URL` (default `http://localhost:4200`).
6. `setupSwagger` (`src/swagger.ts`) serves `/docs` and `/docs-json` unless `SWAGGER_ENABLED=false` or, without that variable, `NODE_ENV=production`. The document itself is built by `createSwaggerDocument` (same file), which `npm run docs:openapi` (`src/scripts/export-openapi.ts`) reuses to write `docs/public/openapi.json` without a database: the app is created with `preview: true`, so providers (and TypeORM) are never instantiated.
7. The server listens on port 3000.

`AppModule` loads configuration from `VETCARE_ENV_FILE` or `.env.mssql.local` (`src/database/database.config.ts`), connects TypeORM to SQL Server (`type: "mssql"`), registers an in-memory throttler (default 5 requests per 15 minutes; no global guard: `ThrottlerGuard` and per-route `@Throttle` limits apply only to the password recovery routes in `src/auth/auth.controller.ts`) and imports `PersistenceModule`, `HttpResponseModule` and the resource modules. `@nestjs/schedule` is used by `src/auth/reset-token.service.ts` (hourly cron).

## Layers

Controller (routing, JWT and role guards, `@ResponseMessage`, `@HttpCode`) -> application service (resource facade) -> BusinessService (access checks, validation, repositories, transactions) -> `PersistenceService` (SQL Server error translation). `HttpResponseModule` wraps results in the response envelope and formats errors; see [api/http-responses.md](api/http-responses.md) (internal) and [public/index.md](public/index.md) (consumer contract).

## Resource organization
Resource code (`src/app/`) is organized into users, employees, roles, job-titles, system-settings, animal, animal-owners, animal-measurements, measurement-types, species, breeds, reservation, reservation-history, blocked-times, employee-schedules, clinic-services (`vc_services` and `vc_employee_services`) and clinical-visits (plus the stateless `availability` read service): one folder per table, with the resource-service layout (entities/, dto/, enums/, *.messages.ts, business service, service, controller and module when there are endpoints).

- `src/app/reservation/`: `vc_reservations` only (entity, DTOs, policy, serializer, controllers, services, module, `employee-schedule-lock.ts`); `GET /api/vetcare/clinic/hours` stays here because it exposes the reservation policy.
- `src/app/reservation-history/`: `vc_reservation_history` (entity, action enum, `ReservationHistoryService`, module without controller). `GET /api/vetcare/reservations/:id/history` remains in the reservations controller and uses the exported service.
- `src/app/animal-owners/`: `vc_animal_owners` (entity, end-reason enum, DTOs, messages, `AnimalOwnersBusinessService`, `AnimalOwnersController`, `AnimalOwnersModule`) plus the read side `AnimalAccessService`/`AnimalAccessModule` (no controller, no application imports), shared by animals, measurements, clinical visits, reservations and accounts without circular imports. See "Animal tutors".
- `src/app/blocked-times/`: `vc_blocked_times` (entity, DTOs, messages, services, controller, module; `/api/vetcare/blocked-times` routes unchanged). Blocks are UTC intervals (`start_at`/`end_at`, possibly spanning days and overlapping); `employee_id` NULL is a clinic-wide closure. `blocked-time.queries.ts` (`overlappingBlocks`) is the read shared by reservations, availability and the employee availability list. The reservation module reads the entity for the block check. See "Employee schedules, blocked times and availability".
- `src/app/employee-schedules/`: `vc_employee_schedules` (entity, DTO, messages, policy, `EmployeeSchedulesBusinessService`, module without controller; `GET/PUT /api/vetcare/employees/:id/schedules` live in `EmployeesController`).
- `src/app/availability/`: `GET /api/vetcare/availability` only (service, policy, DTO, controller, module); stateless, with no table of its own.

Each resource has a controller, an application service, a BusinessService, request DTOs and a dedicated messages file. Controllers handle routing and authentication/role guards. Application services expose resource operations and delegate each call. BusinessServices own access checks, validation, repository work and orchestration. This avoids generic base-service inheritance and keeps resource-specific rules visible.

Animal relation names live in AnimalRelation; reservation relation names live in ReservationRelation. These enums refer to TypeScript relation attributes, not SQL names. SQL mappings continue to use the already-migrated snake_case schema. No database migration is required by this reorganization.


## Persistence errors

PersistenceService.execute wraps repository work. It recognizes SQL Server error numbers centrally: duplicate unique values become HTTP 409, reference conflicts become 409, invalid persisted values become 400, and unclassified QueryFailedError failures become a safe HTTP 500 without SQL or driver details. GlobalExceptionFilter applies the same translator to queries not wrapped explicitly and formats all HTTP errors using the shared response contract. Existing HTTP business exceptions retain their original status. Resource services contain no SQL Server error-number handling; when a resource needs its own message for one rule it uses the helpers exported next to the translator (`isUniqueViolationOf(error, name)`, `isReferenceViolation(error)` — the latter gives DELETE /api/vetcare/services/:id its readable 409 when a foreign key rejects the deletion).

Messages emitted by business rules are stored in the corresponding resource messages file. Enum names represent business concepts rather than copies of entire sentences.


## Lock order

Every transaction acquires row locks (`UPDLOCK`, via `pessimistic_write`) in this single order and never in the reverse direction:

`vc_reservations` -> `vc_animals` -> `vc_clinical_visits` -> `vc_animal_measurements`; `vc_reservations` -> `vc_animals` -> `vc_employees` -> reads of the employee's `vc_users` row and `vc_employee_services` -> insert into `vc_clinical_visits` (visit start); `vc_reservations` -> `vc_animals` -> `vc_users` -> `vc_services` (shared lock, creation only) -> `vc_employees` -> read of `vc_employee_services` -> clinic closures applock (`vc_blocked_times:global`, Shared) -> employee schedule applock (Exclusive, `sp_getapplock`) -> reads under the applocks (schedules, blocks, overlapping CONFIRMED reservations); `vc_services` (shared lock on the services to add, by id) -> `vc_employees` -> writes to `vc_employee_services` (PUT /employees/:id/services; same service -> profile order as reservation creation; reads open reservations without lock hints); `vc_services` alone (service update/deletion; deletion then counts references without lock hints); `vc_reservations` (by id) -> `vc_animals` -> `vc_users` (accounts, by id) -> writes to `vc_animal_owners`/`vc_reservations` (tutorship changes); `vc_users` -> `vc_reset_tokens`; `vc_users` -> `vc_employees` -> `vc_roles` (last-administrator check); `vc_users` -> `vc_animal_owners` (account deletion / CLIENT removal: read primary rows, close secondary rows); `vc_system_settings` -> `vc_job_titles` (setting update; job-title deactivation/deletion locks only the job title and then reads the settings without lock hints).

Exception: PUT /api/vetcare/users/:id/roles takes the administrator role lock and the tutorships before the employee profile; it cannot deadlock with the other account flows (update/deactivation, deletion, password change and reset) because each of them locks the same `vc_users` row first.

- Tutorship changes (add/remove a tutor, transfer, animal creation, PATCH /api/vetcare/animal/:id with another ownerId) lock the animal row before reading `vc_animal_owners` for a decision, and lock every account that gains a row before any `vc_animal_owners` write (two accounts are locked in id order). Removal of a secondary tutor locks, after the animal and before the decision read, the removed tutor's account and (with `transferFutureReservations`) the primary tutor's account, in id order. Account deletion and CLIENT removal lock the account and then read/close its rows without locking the animal, so they serialize on the account row with any flow that would make the account a tutor or remove it; no cycle forms because removal holds no `vc_animal_owners` row lock while waiting for the account, and the account flows never wait for an animal lock (their UPDATE seeks the account's own rows through `ix_vc_animal_owners_user_active`). Animal creation inserts the new animal row first (nobody can be waiting on it), then locks the owner's account, then inserts the primary row.
- Tutorship changes that move reservations (`transferFutureReservations: true`) lock the candidate reservations (open, of the animal, whose client is the leaving tutor) one by one in id order BEFORE the animal (reservation -> animal, the order of confirm/reschedule/visit start). After the animal lock (which also blocks new reservations of the animal, since creation locks it) they are read again; a reservation not locked in the first phase (created in between) makes the request fail with 409 (CONFLICT, "retry" message) instead of locking a reservation while holding the animal, which could deadlock with confirm/reschedule/visit start. Without the flag no reservation is locked: they are only read under the animal lock (409 when any is open).

- Reservation creation (animal -> client account -> service (shared) -> employee profile -> qualification read -> applock), confirmation and reschedule (reservation -> animal -> client account -> employee profile -> qualification read -> applock) and assignment (reservation -> employee profile -> qualification read -> applock). The employee profile is locked without relations and its account is read in a separate statement after the lock is granted, so it sees changes committed by whoever held the lock (also under READ_COMMITTED_SNAPSHOT).
- Services and qualifications: creation reads the service with `pessimistic_read` (`HOLDLOCK, ROWLOCK`, held until commit) so a concurrent deactivation or deletion (which takes `UPDLOCK` on the service and nothing else) either commits first and is seen, or waits; shared locks of concurrent bookings are compatible with each other. The qualification check (`vc_employee_services`, plain read) runs right after the employee profile lock and before the applock, like the account re-read; PUT /api/vetcare/employees/:id/services first reads the current qualifications without locks, derives the services to add and reads them with `pessimistic_read` in id order (validating existence and `isActive` in that read), and only then locks the profile: the order service (shared) -> profile is the one of reservation creation, and PATCH/DELETE /services/:id lock only the service, so no cycle forms (the previous order profile -> service read/FK check could deadlock with a service update waiting behind a booking). Under the profile lock the diff is recomputed; if a service that was not locked must now be added (qualifications changed meanwhile) the request fails with 409 `QUALIFICATIONS_CHANGED` instead of reading an unlocked service while holding the profile. It changes qualifications only while holding the profile lock and then reads the open reservations without lock hints, so removing a qualification and assigning/confirming a reservation for that employee serialize (check-then-act). Assign, confirm and reschedule never read the service row, so an inactive service never blocks them.
- Visit start: reservation -> animal -> employee profile (then the account and qualification reads and the visit insert); complete/void: reservation -> visit; measurements: visit -> measurement.
- Employee termination/unavailability locks the profile and then *reads* the open reservations without lock hints. Account deactivation/deletion locks the account and then the profile; animal deletion locks the animal (animal update and confirm lock only the animal) and then *reads* the open reservations and the IN_PROGRESS visits without lock hints. Creation with an employee, assignment, confirmation and reschedule lock the profile before they write, so they serialize with termination (check-then-act); because those readers never lock reservations, no cycle can form. Starting a visit locks the reservation (if any), the animal and then the responsible employee profile, and reads the account and the qualification after the profile lock (the pattern of the reservation writes). It therefore serializes with termination or unavailability (PATCH /api/vetcare/employees/:id), account deactivation (PATCH /api/vetcare/users/:id with `isActive=false`), account deletion (DELETE /api/vetcare/users/:id), profile deletion (DELETE /api/vetcare/employees/:id) and qualification changes (PUT /api/vetcare/employees/:id/services): a start that waited sees the committed result (terminated or deleted profile, inactive account: 400; qualification removed: 400 `EMPLOYEE_NOT_QUALIFIED`). It also serializes with animal deletion (same animal row). Termination still does not check IN_PROGRESS visits: a visit started before the termination stays IN_PROGRESS.
- Schedule and block applocks (`sp_getapplock`, transaction-owned, 5 s timeout): the clinic closures resource `vc_blocked_times:global` and the employee resource `vc_reservations:employee:<employeeId>`. A timeout, a cancellation or a deadlock victim returns 409 (retry); any other result, or no active transaction, returns 503. Per operation:
  - Global block (`employeeId` NULL): create and update take the closures applock Exclusive; an update then locks the block row (UPDLOCK); both then read the overlapping CONFIRMED reservations without lock hints.
  - Individual block: the employee profile (UPDLOCK), then the employee applock (Exclusive), then the read of that employee's overlapping CONFIRMED reservations.
  - Block PATCH: the applock(s) of the scope come first (for an individual scope, the profile lock before the employee applock), then the block row (UPDLOCK). If the scope changed meanwhile and `employeeId` was omitted: 409 "reload and retry".
  - Block DELETE: the block row (UPDLOCK) only; it takes no applock.
  - PUT schedules: the employee profile (UPDLOCK), then the employee applock (Exclusive), then plain reads of the current rows and of the open reservations, then delete and insert.
  - Occupying flows (creation with an employee, assignment, confirmation, reschedule): closures applock Shared, then the employee applock (Exclusive), then the reads listed in the chain above.
- Why there is no cycle: the closures applock is always taken before any employee applock, never the other way round. No flow waits for an applock while holding a `vc_blocked_times` row: a block PATCH takes its applocks before its row, and a DELETE takes no applock. Tutorship changes, and cancel, no-show and visit completion, never take these applocks. Plain reads of reservations under the applocks take shared locks, which are compatible with the update locks (`UPDLOCK`) held by reservation flows; a plain read can only wait for a row already modified (exclusive lock) by a transaction that never waits for these applocks (cancel, no-show, visit completion, tutorship changes, or a flow that already holds them), so no cycle forms. Under READ_COMMITTED_SNAPSHOT plain reads take no shared locks at all. Applocks are therefore not always the last locks of a chain: a block PATCH locks its row after them.
- Lock waits: `withLockTimeout` (`src/app/core/persistence/lock-timeout.ts`) runs the transactions of reservations, clinical visits (start, update, complete, void and the measurements linked to a visit), blocked times, animal tutors (the /owners and /transfer routes; an owner change through PATCH /api/vetcare/animal/:id runs without the cap) and the employee schedule PUT with `SET LOCK_TIMEOUT 5000`, sent as a batch on the transaction's own connection, so it applies to every query of the transaction. A lock wait longer than 5 s fails with 1222, which is returned as 409 (retry). `SET LOCK_TIMEOUT -1` is sent at the end on a best-effort basis. If the server had already ended the transaction (deadlock victim 1205 or a trigger THROW), that reset fails and is ignored, so the pooled connection keeps the 5 s limit until another critical transaction resets it; in the meantime a lock wait above 5 s on that connection, including non-critical work, returns 409 (retry). No data is affected.
- Clinical integrity triggers (`ClinicalIntegrity1795780800000`, see [database.md](database.md#clinical-integrity-triggers)) are the last line of defence behind the application checks. `tr_vc_clinical_visits_reservation_integrity` refuses changing a visit's `id`, `animal_id` or `reservation_id` (409, 51104) and creating a visit for a reservation that is not CONFIRMED (409, 51105). `tr_vc_reservations_visit_integrity` refuses a reservation becoming COMPLETED without a COMPLETED visit (409, 51106) and becoming CANCELLED, NO_SHOW or PENDING while it has an IN_PROGRESS or COMPLETED visit (409, 51107). Each THROW reaches the client as a 409 with its own message. Each trigger reads the other table `WITH (READCOMMITTEDLOCK)`, so when two transactions interleave, one waits for the other and the worst outcome is a deadlock (1205, 409 for the victim), never invalid data committed. `complete()` updates the visit to COMPLETED before the reservation because the reservation trigger needs a COMPLETED visit in the same transaction; the reverse order fails with 51106.
