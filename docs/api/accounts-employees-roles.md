# Accounts, employees and roles

> [não verificado] routes, roles, the settings cache (60 s) and the rule names were checked against the code; the lock sequences of setting, role and employee updates were not re-traced statement by statement.

## Roles through system settings

Roles are data. Code never references role ids or role codes; it references only `vc_system_settings` keys (`SystemSettingCode`). `SystemRole.ADMIN`, `SystemRole.EMPLOYEE` and `SystemRole.CLIENT` map to `ADMIN_ROLE_ID`, `EMPLOYEE_ROLE_ID` and `CLIENT_ROLE_ID`. `@Roles(...)` receives these keys; `RolesGuard` resolves them through the global `SystemSettingsService` and allows the request when the caller holds ANY resolved role id. A missing or malformed role setting fails closed (500). Settings are cached in memory for 60 seconds per application instance; the instance that serves an update invalidates its own cache after the update transaction ends, while other instances (or direct SQL edits) see the change only after their cache expires, i.e. up to 60 seconds later.

JWT validation loads the user's active roles (`vc_user_roles` joined to active `vc_roles`) and the employee profile (id and termination date). `request.user`/`Actor` contains `id`, `email`, `name`, `roleIds` (lowercase), `isAdmin`, `isEmployee`, `isClient` and `employeeId` (or null). `isEmployee` requires the role of `EMPLOYEE_ROLE_ID` AND an active employee profile (termination NULL or after today); when the role is held without an active profile, the EMPLOYEE role id is also removed from `roleIds`, so `@Roles(EMPLOYEE)` denies access as soon as a termination date passes, even without any save. The JWT payload is unchanged (`sub`, `email`, `name`). Staff means administrator or employee role. Ids are compared case-insensitively because SQL Server returns uniqueidentifier in uppercase.

`GET /api/vetcare/auth/me` returns account data without the password hash, `roles` [{id, code, name}] and `employee` (or null) with `jobTitles` [{id, code, name}]. `role`, `function` and `workLoad` no longer exist in requests or responses.

## Accounts, employees and catalogs

| Resource | Routes | Access |
| --- | --- | --- |
| Roles | GET/POST /api/vetcare/roles, GET/PATCH/DELETE /api/vetcare/roles/:id | ADMIN (callers read their own roles through GET /api/vetcare/auth/me) |
| Job titles | GET/POST /api/vetcare/job-titles, GET/PATCH/DELETE /api/vetcare/job-titles/:id | read: authenticated; write: ADMIN |
| System settings | GET /api/vetcare/system-settings, GET/PATCH /api/vetcare/system-settings/:id | ADMIN |
| Animal verification | PUT /api/vetcare/animal/confirm/:id | ADMIN or veterinarian (`@Roles` ADMIN, EMPLOYEE + check in the service; 403 otherwise) |
| Employees | GET/POST /api/vetcare/employees (GET filter `isAvailableForBookings=true` also requires termination NULL or after today), GET /api/vetcare/employees/me, GET /api/vetcare/employees/available/:date, GET/PATCH/DELETE /api/vetcare/employees/:id | ADMIN; GET /me and GET /:id also for the employee itself |
| User roles | GET /api/vetcare/users/:id/roles (owner or ADMIN), PUT /api/vetcare/users/:id/roles (ADMIN) | |

Role and job-title codes are normalized to uppercase and immutable (409). Referenced entries cannot be deleted (409): deactivate them instead. A role referenced by a `*_ROLE_ID` setting can be neither deleted nor deactivated. Setting codes are immutable and settings are neither created nor deleted through the API; `*_JOB_TITLE_ID` values (`VETERINARIAN_JOB_TITLE_ID`) must be the UUID of an existing, active job title (400; the job-title row is locked during the update) or `null`/`""` to clear it, and a job title referenced by such a setting can be neither deactivated nor deleted (409; the job-title update/delete locks the job-title row and reads `vc_system_settings` from the database in the same transaction, never the settings cache); `*_ROLE_ID` values must be the UUID of an existing, active role (400), must differ from the value of every other `*_ROLE_ID` setting (409), and `ADMIN_ROLE_ID` must reference a role held by at least one active user (409). Validation and save run in one transaction that first locks (UPDLOCK) every `*_ROLE_ID` row and the previous and new role rows, so it serializes with concurrent setting updates and with the last-administrator check.

`PUT /api/vetcare/users/:id/roles` with `{ roleIds: [] }` replaces the whole list in one transaction. New assignments require active roles; existing assignments of since-deactivated roles may be kept. Kept assignments are not rewritten. The last active administrator cannot lose the administrator role, be deactivated or be deleted (409); the administrator role row is locked to serialize concurrent changes.

`POST /api/vetcare/employees` accepts exactly one of `userId` (existing account) or `user` (new account: name, email, optional phone, birthDate, nif), plus employeeNumber, licenseNumber, hireDate, terminationDate, isAvailableForBookings, jobTitleIds, description and notes. Account, role from `EMPLOYEE_ROLE_ID` (only when the created profile is active; a profile created already terminated gets no role, and a new account is then created without roles), profile, job titles and reset token are written in one transaction; the existing employee welcome email is sent after commit when an account was created. `jobTitleIds` on update replaces the assignments. DELETE removes the profile, its job titles and the EMPLOYEE role, keeping the account and its other roles; a profile referenced by any reservation or clinical visit is never deleted (409 IN_USE; the message states how many reservations and clinical visits reference it): terminate it instead. A profile cannot be created for an inactive account, nor reactivated (EMPLOYEE granted again) while its account is inactive (409). These routes replace `POST /api/vetcare/users/employees`, `PATCH /api/vetcare/users/employee/:id`, `GET /api/vetcare/users/available/:date` and `GET /api/vetcare/auth/employees`, which were removed.

Users keep only account data. Public registration (`POST /api/vetcare/users`) and `POST /api/vetcare/users/clients` assign the role from `CLIENT_ROLE_ID` in the same transaction. Emails are trimmed and lowercased, `nif` is a nine-digit string and `birthDate` is YYYY-MM-DD (not in the future). Changing `email` or `isActive` is reserved to administrators. Duplicate email or NIF among non-deleted users returns 409; email and NIF are unique only among non-deleted accounts, so they can be reused after a soft delete. Soft-deleting a user also deletes its reset tokens, and returns 409 while the user has an active employee profile (terminate or delete the profile through `/api/vetcare/employees` first).

Animal owners must hold the client role; staff see all animals and staff-created animals are verified (creation rule unchanged; species/breed changes follow "Integrity and lifecycle"). A reservation's assigned employee is an employee profile (`vc_employees.id`) that is available for bookings, belongs to an active account and has no termination date or one after today and after the reservation date, regardless of roles. Reservations are never self-assigned nor auto-confirmed. Password hashes are never selected or serialized.

Related accounts are projected per caller. In reservation responses, non-administrators see `employee` as `{ id, name, profilePictureUrl }` and `client` as `{ id, name, email, phone }`, and the nested `animal` has no `owner` (it is the client); administrators see full accounts (`id`, `name`, `email`, `phone`, `birthDate`, `nif`, `profilePictureUrl`, `isActive`, `description`, `notes`, timestamps) for client, employee and animal owner. Animal responses expose `owner` as `{ id, name, email, phone }` to non-administrators and as the full account to administrators. Measurement responses carry only `recordedBy` and `updatedBy` (ids), never the account; `updatedBy` (last editor) is visible only to ADMIN and EMPLOYEE and omitted for clients (`projectMeasurement`), in GET/list/POST/PATCH of `/api/vetcare/animal-measurements` and in `latestMeasurements` of animal responses.

## Integrity rules for roles and employees

- An employee profile is active while `termination_date` is NULL or after today (clinic date). An active profile always carries the role of `EMPLOYEE_ROLE_ID`: creating an active profile, or reactivating it (clearing or postponing the termination), grants the role in the same transaction; an update that leaves the profile terminated removes the role in the same transaction (logged after commit with actor, user and timestamp). A termination date that passes without a save is covered by JWT validation (see `isEmployee`). `PATCH /api/vetcare/employees/:id` and the profile check of `PUT /api/vetcare/users/:id/roles` lock the `vc_employees` row (UPDLOCK), so they serialize without relying on blocking reads (READ_COMMITTED_SNAPSHOT). `PUT /api/vetcare/users/:id/roles` returns 409 when it would remove EMPLOYEE from a user with an active profile, and also 409 when it would grant EMPLOYEE to a user without an active profile (the role is never granted for an account alone). Updating `EMPLOYEE_ROLE_ID` returns 409 unless every active employee already holds the new role. `DELETE /api/vetcare/employees/:id` removes the profile, its job titles and the EMPLOYEE role in one transaction.
- When the termination date is today or earlier, `isAvailableForBookings` is forced to false on save; explicitly requesting true for a terminated employee returns 400. Reservation assignment still checks bookability. `users.is_active` (may authenticate) and `employees.is_available_for_bookings` (may be chosen for new bookings) stay independent otherwise. A termination date that passes later does not rewrite the stored flag; the booking check covers it.
- Role assignments record `assigned_by`: the authenticated actor for `PUT /api/vetcare/users/:id/roles`, employee creation/reactivation and `POST /api/vetcare/users/clients`; NULL for public registration and the seed. Replacing roles deletes only removed assignments and inserts only new ones, so kept rows retain their original `assigned_by` and `created_at`. Every assignment and removal of the `ADMIN_ROLE_ID` role is logged through the Nest Logger (actor, target and timestamp) after commit. Role management (roles catalog, user roles and system settings) is restricted to ADMIN; account-creation paths can only assign EMPLOYEE or CLIENT.
- An account may be client and employee at once (e.g. a veterinarian with her own pet): neither `PUT /api/vetcare/users/:id/roles` nor `POST /api/vetcare/employees` (existing user) makes the roles exclusive, and granting EMPLOYEE never removes CLIENT. Animal owners and reservation clients only need CLIENT, and `/api/vetcare/auth/me` returns every active role plus the employee profile. Access to other clients' data comes only from the professional path (administrator, or EMPLOYEE with an active profile); otherwise CLIENT limits the caller to their own data and adds nothing for staff. When staff act on their own account as clients they follow the client path: a reservation for their own animal (no `ownerId` or `ownerId` = self, CLIENT required) is not self-assigned and stays `PENDING`, and an animal they register for themselves is not auto-verified (administrators excepted). Responses are projected by `isAdmin` only, so such an account sees reduced related accounts.
- SQL Server error 547 is split by the driver message: CHECK constraint violations return 400 ("A value does not satisfy the rules required for this record"); FOREIGN KEY/REFERENCE violations keep returning 409.
- Local login rejects inactive and soft-deleted accounts, and JWT validation reloads the account on every request, so a token issued before deactivation or deletion stops working immediately.
- JWT validation also rejects a token whose `iat` (seconds) is earlier than the second of `vc_users.password_changed_at`, so a password reset or change ends every session issued before it, including the one used for `POST /api/vetcare/auth/change-password` (that endpoint returns a replacement token, see below). A login in the same second as the change keeps working; accounts without `password_changed_at` are unaffected.
